# Представляем Enginet - мультиагентную (гибридную) систему планированияы

Наша система представляет собой веб-сервис, который автоматически распределяет заявки между выездными инженерами и строит для каждого маршрут на день с учётом квалификации, доступного транспорта и временных окон заявок. Систему можно назвать гибридной, т.к. она сочетает в себе как мультиагентный подход (по принципу "аукциона", об этом ниже), так и алгоритмы фильтрации (строгого отбора) по тем критериям, которые это позволяют.

## <a name="actual"></a> 1. Актуальность

Выездные инженерные службы ежедневно сталкиваются с одной и той же операционной проблемой: диспетчер вручную распределяет десятки заявок между исполнителями, одновременно держа в голове квалификацию каждого инженера, какой у него транспорт, какое оборудование ему выдано, укладывается ли он по времени в свою смену и во временное окно клиента. Ручное распределение не масштабируется - при появлении срочной заявки или внезапной недоступности инженера весь план приходится пересобирать заново, и на это уходят десятки минут, в течение которых бригады простаивают, а клиенты не получают подтверждённого времени визита.

Задача становится ещё более выраженной у крупных операторов связи, где объём заявок на подключение, ремонт и аварийные работы исчисляется сотнями в день на район, а стоимость ошибки диспетчера - это либо пропущенное окно визита, либо избыточно занятые в разъездах бригады. Сервис снимает эту нагрузку с диспетчера: система сама подбирает исполнителя под заявку, строит для него маршрут и в понятной форме объясняет, почему решение принято именно так, а при изменении обстановки - оперативно пересобирает только затронутую часть плана, не трогая уже согласованные маршруты остальных инженеров.

## <a name="cnp"></a> 2. Ключевое архитектурное решение: Contract Net Protocol

В основе планировщика лежит мультиагентный протокол **Contract Net Protocol**: на каждую заявку одновременно и независимо друг от друга откликаются все агенты-инженеры, каждый сам оценивает, подходит ли ему эта работа, и участвует в «торгах» за неё, а система выбирает победителя по заранее известным правилам. Соответствие классической схеме CNP:

| Этап CNP                 | Как реализовано                                                                                                                        |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Объявление задачи**    | Заявка выставляется на аукцион в порядке приоритетной очереди                                                                          |
| **Заявки от агентов**    | Каждый агент-инженер независимо проверяет заявку через собственный жёсткий фильтр и, если она ему проходит, то формируется предложение |
| **Выбор победителя**     | Система выбирает лучшее предложение по явной иерархии критериев                                                                        |
| **Исполнение контракта** | Заявка вставляется в маршрут победившего инженера                                                                                      |

Преимущества этого подхода перед единой централизованной оптимизацией:

- **Прозрачность решения.** Каждый отказ агента от заявки - это конкретная, зафиксированная причина (не тот навык, не тот район, нет нужного оборудования, не влезает по времени), поэтому объяснение диспетчеру строится напрямую из трассы торгов, а не реконструируется постфактум.
- **Локальность изменений.** В случае изменения ситуации с заявками в течение дня (новая срочная заявка, отмена, недоступность инженера) на аукцион пересоставляются только напрямую затронутые заявки - маршруты остальных инженеров, уже согласованные ранее, не трогаются и не пересчитываются с нуля.
- **Расширяемость.** Чтобы добавить новое ограничение или изменить логику отбора, достаточно поменять фильтр агентов - не нужно перестраивать модель оптимизации.
- **Устойчивость к неполной информации.** Если часть заявок физически невозможно закрыть (нет свободных исполнителей на нужное время, отсутствует навык или оборудование), система не падает и не блокирует весь план - просто эти заявки остаются не назначенными с явно указанной причиной.

После основного аукционного прохода запускается отдельный шаг локальных улучшений: консолидация заявок на меньшем числе исполнителей и 2-opt (эвристика локального поиска) оптимизация маршрута внутри маршрута каждого инженера для сокращения пробега - оба шага работают только поверх уже принятых решений и не могут ухудшить то, что уже назначено.

## <a name="schema"></a> 3. Краткая схема решения

**Интерфейс:** 
- React (Vite) + react-leaflet. 
- Четыре вкладки: 
  1) Офисы
  2) Инженеры (профиль, район, доступность, оборудование)
  3) Заявки (импорт из CSV, ручное добавление, правка)
  4) План (карта с маршрутами, метрики, объяснения, события дня)

*План пересчитывается автоматически после любого изменения данных.*

**Алгоритм:**
- FastAPI-бэкенд на Python, без ORM/БД
- Планирование - CNP-аукцион
- Вставка заявки в маршрут
- Локальная оптимизация маршрута
- *События дня (срочная заявка / отмена / возврат отменённой / недоступность инженера)
переторговывают только напрямую затронутые заявки, не перестраивая план
с нуля.*

**Данные:**
- Импорт заявок и бригад - из CSV (можно загрузить сразу
несколько файлов)
- Геокодирование адресов и расчёт маршрутов - через Yandex Geocoder API и Yandex Router API, с возможностью построения маршрутов при на отсутствия ключа (*подробнее в разделе 5*).

## <a name="dataset"></a> 4. Особенности тестового датасета

### <a name="req_file"></a> 4.1. Файл заявок (CSV)

|         Поле          |                                                  Описание                                                  |       Формат/единицы        |
| :-------------------: | :--------------------------------------------------------------------------------------------------------: | :-------------------------: |
|        Заявка         |                                                 ID заявки                                                  |            Число            |
|     Тип заявки BK     |     Локальная заявка / Подключение / Дозаказ / Глобальная проблема - маппится в навык (см. пункт 4.3)      |    Текст из справочника     |
|       Статус BK       |                                Статус заявки в исходной системе, справочно                                 |            Текст            |
|     Тип заявки HD     |               Используется только как справочный текст причины, не участвует в отборе агента               |            Текст            |
|  Начало / Окончание   |                                           Временное окно визита                                            |     `ДД.ММ.ГГГГ ЧЧ:ММ`      |
|         Район         |                     **Не читается парсером** - район заявки определяется именем файла                      |              -              |
|         Адрес         |                                  Адрес визита, геокодируется при импорте                                   |            Текст            |
|        Бригада        |                                            Наименование бригады                                            |            Текст            |
|      Подключение      |    Тип подключения FMC / FTTB / пусто - требует соответствующего дополнительного оборудования у бригады    |    Текст из справочника     |
| Требуемые инструменты | Необязательная колонка, список через запятую - дополнительное оборудование, которое обязано быть у бригады | Текст, список через запятую |

Длительность работы в CSV не передаётся (только двухчасовое окно), поэтому при импорте проставляется дефолт по навыку (ремонт - 60 мин, новое подключение - 90 мин, авария - 45 мин). При чем, оператор может поправить длительность у любой заявки через интерфейс.

Один и тот же файл можно импортировать повторно без дублирования: офис ищется по нормализованному адресу, заявка - по её ID, уже существующие записи не затираются свежими (иначе назначенная или отменённая заявка при повторной загрузке того же CSV откатилась бы в статус «не назначена»).

### <a name="brigade_file"></a> 4.2. Файл бригад (CSV)

|     Поле     |                                                      Описание                                                       | Формат/единицы |
| :----------: | :-----------------------------------------------------------------------------------------------------------------: | :------------: |
|   Бригада    |                                                Наименование бригаты                                                 |     Текст      |
| Компетенции  |                                      Аварийные работы/ремонт/новое подключение                                      |     Текст      |
| Оборудование | Оборудование для ремонта, оборудование для аварийных работ, оборудование для подключения, оборудование для FMC/FTTB |     Текст      |
|  Транспорт   |                               Автомобиль, пешеход, велосипед, общественный транспорт                                |     Текст      |

*Транспорт и район (из блока «Район» под таблицей заявок соответствующего файла) берутся из файла автоматически, вручную при импорте задаётся только смена бригады. Район бригады совпадет с районом уже импортированных заявок - именно из него определяется привязка к офису.*

### <a name="refs"></a> 4.3. Справочники

**Требуемый навык (из «Тип заявки BK»):**
1. Локальная заявка - Ремонт
2. Подключение / Дозаказ - Новое подключение
3. Глобальная проблема - Авария

**Типы транспортных средств:** 
- Автомобиль
- Пешеход
- Велосипед
- Общественный транспорт

*По одному на инженера. Может указываться в требовании для заявки.*

**Оборудование:** 
- Основное (Оборудование для ремонта / для подключения /для аварийных работ) определяет навык бригады
- Дополнительное - оборудование для FMC, для FTTB

**Приоритет заявки:** 
1. Любая заявка с флагом "Срочно" (ставится только оператором)
2. Новое подключение и авария
3. Ремонт

## <a name="yandex"></a> 5. Работа без ключей Yandex API и индикатор в интерфейсе

Сервис полностью работоспособен и без ключей Yandex - это нужно для демонстрации в условиях, когда ключ ещё не выдан, закончилось действие пробного периода или недоступен интернет. Текущий статус интеграции виден прямо в интерфейсе: в боковой панели, в её нижней левой части, находится индикатор состояния геокодирования и маршрутизации - он показывает, работает ли сейчас реальный Yandex API или сервис работает в автономном (кончился срок действия ключа, ключ не задан, либо
запросы к API стабильно не проходят).

Что при этом меняется:
- **Геокодирование.** Без ключа или при его истечении адрес превращается в детерминированные псевдокоординаты
  (один и тот же адрес всегда даёт одну и ту же точку, но она не соответствует реальному расположению дома). При выключенном или нерабочем геокодере карта теряет смысл целиком: адреса точек не будут соответствовать их фактическому расположению на местности - сама логика планирования при этом продолжает работать корректно, но визуализация становится не показательной.
- **Маршрутизация.** Без ключа время и расстояние считаются по прямой между точками с коэффициентом искревления дороги и средней скоростью для вида транспорта, карта в этом режиме рисует прямые линии, а не реальную геометрию улиц. Алгоритм распределения заявок при этом так или иначе продолжает работать в полном объёме - просто с меньшей точностью оценки времени в пути и пробега, чем при действующем ключе, который возвращает настоящую геометрию дороги и прогноз пробок.

### <a name="yandex_key"></a> Как получить ключ API

Ключи Yandex Geocoder и Router API кладутся в `backend/.env` (по образцу`backend/.env.example`) и подхватываются автоматически при запуске - без ключей демонстрация тоже полностью проходит, но по указанным выше причинам точность карты и оценок времени будет ниже. Два варианта, как получить рабочий ключ на момент проверки:

1. **Написать нам** - контакт для получения готового ключа: **@wolf_lm - telegram**. При наличии технической возможности мы включим действующий ключ к моменту начала проверки решения.
2. **Получить ключ самостоятельно** в личном кабинете [developer.tech.yandex.ru](https://developer.tech.yandex.ru/) (отдельно для геокодера и для Router API) и вписать его в `backend/.env` - займёт несколько минут.

## <a name="limits"></a> 6. Известные ограничения прототипа

- Жадный однопроходный аукцион - не гарантирует глобальный оптимум по числу задействованных исполнителей или суммарному пробегу; консолидация и 2-opt после основного прохода улучшают результат локально, но не доказывают оптимальность.
- «Широта навыков» инженера при выборе победителя торгов учитывается как простое число его навыков, а не как фактическая востребованность этих навыков в оставшейся очереди заявок на день.
- 2-opt сокращает пробег только внутри маршрута одного инженера - перенос заявок между инженерами ради чистого сокращения пробега не реализован.
- Состояние существует только в памяти процесса - перезапуск обнуляет офисы, инженеров, заявки и план.
- У API «Получение деталей маршрута» нет отдельного бесплатного тарифа в официальном описании Yandex - лимиты и условия по ключу стоит уточнять в личном кабинете, прежде чем гонять на нём много тестовых прогонов.

## <a name="ideas"></a> 7. Идеи дальнейшего развития

- Полноценный контроль симулированного времени дня в интерфейсе - с разделением плана на выполненные, текущие и предстоящие визиты.
- Более точный критерий «универсальности» инженера при выборе победителя торгов - с учётом фактического остатка заявок каждого профиля в очереди, а не просто числа навыков.
- Меж инженерный локальный поиск, сокращающий суммарный пробег (не только ради консолидации на меньшем числе исполнителей).
- Постоянное хранилище состояния вместо памяти процесса - для работы сервиса не только в рамках одной демонстрационной сессии.
- Прогноз опозданий и сравнение нескольких альтернативных вариантов плана по метрикам эффективности - как отдельная надстройка поверх базового аукциона.

## <a name="run"></a> 9. Как запустить

### Самый быстрый способ - один файл

- **Windows**: дважды кликните `run.bat` в корне проекта.
- **macOS/Linux**: `./run.sh` из корня проекта (при первом запуске может понадобиться `chmod +x run.sh`).

Скрипт сам, по порядку: проверяет, что установлены Python и Node.js; при первом запуске создаёт виртуальное окружение backend и ставит зависимости, а также npm-пакеты фронтенда; поднимает backend (порт 8000) и frontend (порт 5173); открывает браузер на `http://localhost:5173`.

Если положить в `backend/.env` файл с ключами Yandex (скопировав `backend/.env.example` и заполнив) - скрипты запуска подхватят их автоматически.

### Вручную, шаг за шагом

#### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Ключи Yandex - по желанию, см. раздел 5. Без них сервис работает в fallback-режиме.
cp .env.example .env
# ...заполнить .env реальными ключами, затем экспортировать, например:
export $(grep -v '^#' .env | xargs)

uvicorn app.main:app --reload --port 8000
```

Сервис поднимется на `http://localhost:8000`. Проверить: `GET /api/status`.

#### Frontend

```bash
cd frontend
npm install
npm run dev
```

Приложение поднимется на `http://localhost:5173` и обращается к backend по адресу `http://localhost:8000/api` (`src/api.js`).

### Быстрый прогон демо-сценария

1. Вкладка **Заявки** - импортировать файл заявок из `backend/sample_data`.
2. Вкладка **Инженеры** - импортировать файл бригад или завести профили вручную (навык, смена, транспорт, район, оборудование).
3. Вкладка **План** - план построен автоматически.
4. Открыть заявку, посмотреть объяснение назначения. Добавить срочную заявку, отменить существующую или сделать инженера недоступным - увидеть автоматический пересчёт затронутой части плана.
