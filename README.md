# Диспетчер маршрутов инженеров — мультиагентная система планирования

Веб-сервис, который распределяет заявки между инженерами и строит для каждого
маршрут на день, используя параллельный аукцион независимых агентов (по
одному на инженера) вместо централизованного оптимизатора.

Коротко: агент-инженер сам проверяет, подходит ли ему заявка (навык, район,
транспорт, время), и если да — участвует в торгах за неё вместе со всеми
остальными агентами параллельно. Побеждает тот, кто помогает держать меньше
уникальных исполнителей (это приоритетнее), а среди равных — кто быстрее
доберётся. После первого прохода система пытается сама себя улучшить:
объединяет заявки на меньшем числе инженеров и сокращает пробег локальными
перестановками.

## Как запустить

### Самый быстрый способ — один файл

- **Windows**: дважды кликните `run.bat` в корне проекта (или запустите его из
  `cmd`/PowerShell — работает одинаково).
- **macOS/Linux**: `./run.sh` из корня проекта (при первом запуске может
  понадобиться `chmod +x run.sh`).

Скрипт сам, по порядку:
1. проверяет, что установлены Python и Node.js (если нет — подскажет, что
   поставить, и остановится, не сломав ничего);
2. при первом запуске создаёт виртуальное окружение backend и ставит
   зависимости (`pip install`), а также ставит npm-пакеты фронтенда — при
   повторных запусках эти шаги пропускаются, если всё уже стоит;
3. поднимает backend (порт 8000) и frontend (порт 5173) каждый в своём окне
   терминала;
4. сам открывает браузер на `http://localhost:5173`.

Если положить в `backend/.env` файл с ключами Yandex (скопировав
`backend/.env.example` и заполнив) — `run.bat`/`run.sh` подхватят их
автоматически, ничего экспортировать вручную не нужно.

Остановка — просто закрыть оба открывшихся окна терминала (Windows) или
нажать `Ctrl+C` в окне, откуда запускали `run.sh` (macOS/Linux).

На Windows `run.bat` работает через `cmd`, а не PowerShell, поэтому проблема
с политикой выполнения скриптов (`Set-ExecutionPolicy`), с которой можно
столкнуться при ручном запуске, тут просто не возникает.

Если предпочитаете видеть и контролировать каждый шаг вручную (или нужно
что-то нестандартное) — ниже описан ручной способ, шаг за шагом.

### Вручную, шаг за шагом

#### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # необязательно, но рекомендуется
pip install -r requirements.txt

# Ключи Yandex — по желанию. Без них сервис работает в fallback-режиме
# (см. раздел "Fallback-режим" ниже).
cp .env.example .env
# ...заполнить .env реальными ключами, затем экспортировать, например:
export $(grep -v '^#' .env | xargs)

uvicorn app.main:app --reload --port 8000
```

Сервис поднимется на `http://localhost:8000`. Проверить: `GET /api/status`.

Перед запуском сервера имеет смысл прогнать автономные проверки (без сети,
без FastAPI, только чистый Python) — они и раньше гоняли всю логику на
реальном файле "Восток":

```bash
cd backend
python3 selfcheck.py          # ядро: аукцион, вставка в маршрут, события
python3 selfcheck_store.py    # CRUD-слой, ошибки валидации
python3 selfcheck_routing.py  # парсинг ответа Yandex Router API (офлайн, на примерах из доков)
```

#### Frontend

```bash
cd frontend
npm install
npm run dev
```

Приложение поднимется на `http://localhost:5173` и обращается к backend по
адресу `http://localhost:8000/api` (захардкожено в `src/api.js` — при
необходимости поменяйте `BASE`).

#### Быстрый прогон демо-сценария

1. Вкладка **Заявки** → импортировать `backend/sample_data/vostok_sample.csv`
   (или ваш собственный файл/несколько файлов сразу).
2. Вкладка **Инженеры** → завести 4–6 профилей: указать типы заявок, смену,
   транспорт и **район** — выбирается из подсказки, которая заполняется
   районами уже загруженных заявок; офис (стартовая точка) подставляется
   автоматически — тот же, что закреплён за выбранным районом, отдельно
   выбирать его не нужно.
3. Вкладка **План** → план уже построен автоматически (пересчитывается сам
   после любого изменения — не нужно ничего нажимать); кнопка «Обновить» там
   лишь подтягивает свежее состояние с сервера, если экран открыт долго.
4. Там же можно попробовать отменить заявку, вернуть её, сделать инженера
   недоступным (кнопки прямо в таблицах на вкладках «Заявки»/«Инженеры») и
   увидеть автоматический пересчёт.

## Fallback-режим и статус интеграции с Yandex API

`app/geocoding.py` (`_call_yandex_geocoder_sync`) и `app/routing.py`
(`_call_yandex_router_sync`) — обе функции сверены построчно с официальной
документацией Yandex (geocoder и
[Router API](https://yandex.ru/maps-api/docs/router-api/)). У router-функции
по пути нашлось и было исправлено три реальные ошибки, написанные по памяти
на более ранней стадии проекта:
1. неверные названия режимов транспорта (`cycling`/`masstransit` вместо
   правильных `bicycle`/`transit`);
2. неверная структура разбора ответа (код пытался читать
   `legs[0].distance.value`, как у Google Directions API, а у Яндекса нужно
   суммировать поля `length`/`duration` по всем `steps` внутри `leg`);
3. **`departure_time` безусловно передавался в запрос, а Яндекс отвечает
   400 Bad Request на КАЖДЫЙ запрос, где это время в прошлом** — что
   реально произошло при первом боевом тесте: система работает с
   фиксированной тестовой датой сценария (17.08.2026), которая к моменту
   реального использования оказалась в прошлом относительно настоящего
   времени, из-за чего 100% запросов к Router падали. Теперь параметр
   просто не передаётся, если он в прошлом — Яндекс в этом случае сам
   использует прогноз пробок на момент обработки запроса.

Все три ошибки проверены офлайн-тестом `selfcheck_routing.py` на точных
примерах ответа из документации Яндекса (без сети — ответ API замокан), в
том числе третья — отдельным тестом, что `departure_time` из прошлого не
попадает в URL запроса, а из будущего — попадает. Живой вызов с реальным
ключом и реальными координатами при этом по-прежнему не выполнялся в этой
песочнице (нет сети) — если что-то ещё не так с реальным ответом API,
сверьтесь с `GET /api/status` и полем `routing_warnings` там же, оно
покажет текст последней ошибки от API, а `routing_stats` — реальное число
успехов/сбоев/откатов на fallback (не путать с `routing_fallback`, которое
означает только "ключ не задан").

Без ключей сервис не падает и полностью пригоден для демонстрации и
разработки:
- **Геокодирование**: адрес детерминированно превращается в псевдокоординаты
  внутри примерного bounding box Москвы (хэш строки → точка). Один и тот же
  адрес всегда даёт одну и ту же точку, но она **не соответствует реальному
  расположению дома** — расстояния и картинка на карте физически
  бессмысленны, хотя вся логика планирования (фильтры, вставка в маршрут,
  метрики, объяснения) работает корректно на любых координатах.
- **Маршрутизация**: время и расстояние считаются по прямой (haversine) с
  коэффициентом непрямоты дороги и средней скоростью для вида транспорта
  (`app/config.py` → `FALLBACK_SPEED_KMH`), fallback-режим геометрии не даёт
  вовсе — карта в этом режиме рисует прямые линии между точками.
- При подключённом Router API карта рисует настоящую геометрию дороги
  (`polyline` от Яндекса, участок за участком) — см. детали ниже, в
  «Известных упрощениях».

**Про стоимость:** у "API Получение деталей маршрута" (в отличие от
геокодера) нет отдельного бесплатного тарифа в официальном описании —
уточните лимиты и условия по вашему ключу в личном кабинете
([developer.tech.yandex.ru](https://developer.tech.yandex.ru/)), прежде чем
гонять на нём много тестовых прогонов.

## Ключевые решения и где посмотреть код

- **Иерархия жёсткого фильтра** (агент выбывает на первом же несовпадении):
  доступен → навык → **район** (точное совпадение, обязателен) →
  **оборудование** (всё `required_equipment` заявки должно входить в
  `equipment` бригады, точное совпадение строк) → требуемый
  транспорт (если задан у заявки) → физическая возможность вставки в
  маршрут с учётом времени в пути, окна и смены. `app/agents.py::make_bid`.
  Район у заявки — это ИМЯ ФАЙЛА, из которого она импортирована (без
  расширения), а не колонка «Район» внутри CSV: если файлы называются
  `Восток.csv`, `Юго-Восток.csv`, `Югоцентр.csv`, ровно эти три строки и
  становятся районами. Колонка «Район» в самих CSV (конкретные московские
  районы вроде «Кузьминки») не читается и не участвует в отборе —
  осознанное решение оператора. `app/csv_import.py`. Этот же критерий
  учитывается и в раунде локальных улучшений (`_try_consolidate`), чтобы
  оптимизация не переносила заявку инженеру не того района ради красивой
  метрики.
- **Иерархия приоритетов при распределении** (актуальная, уточнённая оператором):
  1. Максимум закрытых за день заявок — важнее не потерять заявку, даже
     если её придётся отдать не самому близкому исполнителю.
  2. Минимум задействованных исполнителей (плотное расписание у занятых) —
     но только пока это не отменяет ни одно уже сделанное назначение.
  3. Внутри аукциона за конкретную заявку — сначала более широкий универсал
     (больше навыков у инженера), и лишь при равенстве — расстояние/скорость
     прибытия. Логика (уточнена оператором): узкого специалиста нечем
     подменить, когда заявок именно его профиля не осталось — он просто
     простаивает; универсала же можно занять плотно чем угодно весь день,
     поэтому именно ему заявку стоит отдавать в первую очередь.
  4. Расстояние/скорость прибытия — самый низкий приоритет, чисто
     тай-брейк между уже допустимыми и равными по широте навыков кандидатами.

  Реализовано это НЕ единой формулой скоринга, а разделением на два
  последовательных шага: аукцион (`app/agents.py::pick_winner`) выбирает
  среди допустимых кандидатов сначала самого широкого универсала, при
  равенстве — самого быстрого, и без предпочтения "уже занятых" инженеров,
  чтобы не забивать чьё-то расписание сверх меры и не лишать более поздние
  по очереди заявки шанса найти исполнителя (это и обеспечивает приоритет
  №1). Консолидация на меньшем числе исполнителей (приоритет №2) вынесена
  в отдельный шаг ПОСЛЕ основного прохода (`app/planner.py::_try_consolidate`)
  — он переносит только уже назначенные заявки, поэтому в принципе не
  может испортить приоритет №1, а только улучшить приоритет №2.
- **Очередь обработки заявок аукционом** (`app/planner.py::_priority_order`)
  — отдельный от иерархии выше вопрос: в каком порядке заявки вообще
  попадают на аукцион, а не кто из инженеров их получает. Три уровня:
  1. срочность — ручной флаг оператора (см. следующий пункт), самый
     сильный сигнал;
  2. заявки на подключение/дозаказ (навык "Работы на подключение и
     дозаказы") — коммерческий приоритет, обрабатываются раньше локальных
     и аварийных при равной срочности;
  3. время начала окна — более ранние заявки вперёд, как и раньше.

  Важно: ручная срочность на заявке любого другого типа всё равно
  перевешивает приоритет подключения — иначе флаг "Срочная" потерял бы
  смысл для локальных и аварийных заявок.
- **Срочность — исключительно ручной флаг оператора**, никакой
  автоматики по типу заявки нет (в т.ч. для типа «Авария» — было
  наоборот на промежуточном этапе разработки, но отменено по явному
  запросу оператора). Оператор свободно включает и снимает срочность у
  любой заявки любого типа. `app/csv_import.py`,
  `app/store.py::add_manual_request/update_request`.
- **Вставка в маршрут** — cheapest insertion: перебираются все позиции в
  текущем маршруте инженера, выбирается допустимая с минимальным приростом
  пробега. `app/route_sim.py::find_best_insertion`.
- **Локальные улучшения после первого прохода**: (1) консолидация — если у
  инженера ровно одна заявка, система пытается перенести её к уже занятому
  инженеру, если это возможно без нарушения ограничений; (2) 2-opt по
  каждому маршруту отдельно для сокращения пробега. Повторяется раундами,
  пока есть изменения. `app/planner.py::run_improvement`.
- **События** (новая заявка / отмена / возврат отменённой / недоступность
  инженера) не перестраивают план с нуля — они переторговывают только
  напрямую затронутые заявки поверх уже согласованных маршрутов остальных
  инженеров, и затем прогоняют раунд локальных улучшений.
  `app/planner.py::event_*`.
- **План пересчитывается автоматически** после любого изменения — не только
  события дня, но и правка профиля инженера, окна/длительности заявки,
  импорт нового файла и т.д. Для событий дня используется точечный
  пересчёт (см. выше), для остальных изменений (могут затронуть уже
  устоявшиеся назначения непредсказуемо) — полный `build_full_plan`.
  Кнопка «Построить план» на фронтенде убрана за ненадобностью — она
  осталась только как API-эндпоинт для ручного форс-пересчёта
  (`POST /api/plan/build`).
- **Повторный импорт того же файла не дублирует ни офис, ни заявки**: офис
  ищется по нормализованному адресу, заявки — по id (совпадает, если это
  тот же номер заявки из того же файла), уже существующие записи не
  затираются свежими (иначе назначенная/отменённая заявка откатилась бы в
  статус «не назначена» при повторной загрузке того же CSV).
- **Офис у инженера определяется автоматически по району**, а не
  выбирается вручную: `Office.districts` — список районов, которые
  обслуживает этот офис (обычно один, но может быть несколько, если
  несколько файлов с разными названиями указали один и тот же адрес офиса
  — дедупликация по адресу, см. пункт выше). При создании/редактировании
  инженера офис ищется по выбранному району автоматически
  (`store.py::find_office_for_district`); если подходящего офиса нет —
  понятная ошибка с объяснением, что нужно сначала импортировать файл для
  этого района. `app/models.py::Office.districts`,
  `app/store.py::add_engineer/update_engineer`.
- **Объяснения** — целиком шаблонные (без LLM), строятся из
  структурированной трассы решения (какие агенты отсеялись и почему, кто
  выиграл торги и почему). `app/explain.py`.

## Известные упрощения (честно, чтобы не было сюрпризов)

- **Нет симулированных "текущих часов"**: план не делит день на "уже
  пройдено" / "ещё впереди". Событие просто трогает только напрямую
  затронутые заявки (новую / отменённую / освободившиеся от недоступного
  инженера), поэтому чужие маршруты стабильны, но нет отдельного контрола
  "сейчас %HH:MM" в интерфейсе. Если для демонстрации это важно — добавляется
  сравнительно небольшим изменением в `planner.py` (поле `simulation_time`
  в `PlannerState` + фильтрация уже наступивших остановок при пересчёте).
- **Polyline на карте — реализовано.** Backend получает геометрию маршрута
  от Router API (`TravelEstimate.polyline`), прокидывает её через
  `RouteStop.polyline` в API-ответ (`[[lat, lon], ...]` на каждую
  остановку — участок геометрии от предыдущей точки), а `MapView.jsx`
  рисует по ней реальную линию маршрута; там, где полилинии для какого-то
  участка нет (fallback-режим без ключа, или единичный сбой конкретного
  запроса) — для этого участка рисуется прямая линия, как раньше, только
  локально, не портя весь маршрут целиком.
- **Поиск позиции вставки заявки распараллелен по кандидатным позициям**
  (`route_sim.py::find_best_insertion`, через `asyncio.gather`) — это стало
  существенно после подключения Router API: при fallback-режиме перебор
  позиций был мгновенным (просто арифметика), а с реальными сетевыми
  запросами последовательный перебор превращался в долгую цепочку HTTP-
  запросов и ощущался как "зависание" интерфейса при любом действии,
  запускающем полный пересчёт плана (например, добавление инженера).
  Внутри одного маршрута шаги по-прежнему считаются последовательно (время
  прибытия на каждую следующую точку зависит от предыдущей — это
  принципиально нельзя распараллелить), но РАЗНЫЕ кандидатные позиции
  вставки друг от друга не зависят и теперь считаются одновременно.
- На фронтенде у всех запросов теперь есть таймаут (2 минуты,
  `frontend/src/api.js`) — это подстраховка на случай, если что-то всё
  равно окажется медленнее ожидаемого (например, при большом плане и
  холодном кэше маршрутов): кнопка корректно разблокируется с понятной
  ошибкой вместо бесконечного "зависания", которое раньше снималось только
  перезагрузкой страницы.
- **Диагностика Router API стала честной.** Раньше `/api/status` показывал
  `routing_fallback: false` при простом наличии ключа — даже если реальные
  запросы к Яндексу все до одного падали (например, по таймауту) и тихо
  откатывались на fallback, счёт "работает по-настоящему" всё равно был
  зелёным. Теперь `routing.py` считает реальные успехи/сбои/откаты
  (`get_stats()`), это видно и в `/api/status` (`routing_stats`), и прямо
  в боковой панели интерфейса — там же, где раньше был только индикатор
  "есть ключ / нет ключа". Если видите "сбои у Yandex API" — текст
  последней ошибки смотрите в `routing_warnings` там же.
- Ограничил число ОДНОВРЕМЕННЫХ запросов к Router API восьмью
  (`routing.py::_CONCURRENCY_LIMIT`) — после того как поиск позиции вставки
  стал параллельным, система могла выстрелить сразу десятками запросов
  разом, что реалистично упирается в лимит Яндекса на конкурентные
  соединения/RPS и вызывает именно те тихие сбои, что описаны в пункте
  выше. Заодно поднял таймаут одного запроса с 5 до 10 секунд
  (`config.py::HTTP_TIMEOUT_SEC`) — транзитная маршрутизация обычно
  считается заметно дольше автомобильной.
- **Прогноз пробок по факту всегда "на текущий момент", а не на
  симулированное время суток из тестового сценария.** Раз `departure_time`
  из прошлого (а тестовые данные почти всегда используют фиксированную
  демонстрационную дату, которая рано или поздно окажется в прошлом
  относительно реального "сейчас") теперь не передаётся вовсе, Яндекс
  считает маршрут с прогнозом пробок на момент обработки запроса — то есть
  для автомобильного маршрута цифры времени в пути отражают, условно,
  "какие пробки сейчас по-настоящему в Москве", а не "какие были бы пробки
  в 8 утра по сюжету демо-сценария". Для пешеходов/велосипеда/самоката это
  не имеет значения (там пробки не считаются в принципе), для общественного
  транспорта результат ближе к реальности, чем к сценарию (используется
  ближайшее по времени реальное расписание). Если для демонстрации
  принципиально важен именно прогноз на конкретный час суток сценария —
  это решается заменой фиксированной демо-даты на реальную ближайшую дату
  при генерации тестовых данных, а не правкой этого файла.
- **Жадный алгоритм с однопроходной обработкой заявок — не точный оптимум.**
  Заявки торгуются последовательно (в порядке приоритета), и решение по
  каждой фиксируется сразу же. Это значит, что теоретически возможна
  ситуация, где другая комбинация назначений закрыла бы на одну заявку
  больше — полноценный перебор/ILP-решатель для этого не реализован
  (осознанно, ради простоты и скорости на масштабе хакатона). Консолидация
  и 2-opt после основного прохода немного улучшают ситуацию, но не
  гарантируют глобальный оптимум ни по одному из приоритетов.
- **"Широта навыков" считается просто числом навыков у инженера**, а не
  фактическим наличием подходящих заявок каждого профиля в очереди на
  оставшуюся часть дня (условно: инженер с тремя навыками предпочитается
  как универсал, даже если по факту заявок двух из этих трёх профилей
  сегодня вообще не осталось, и его "запасная" гибкость на деле не
  понадобится). Более точный вариант — смотреть, сколько ещё заявок каждого
  профиля предстоит распределить, а не просто число навыков — не
  реализован, чтобы не усложнять эвристику сверх необходимого для масштаба
  задачи.
- **2-opt только внутри маршрута одного инженера.** Между инженерами
  локальный поиск переносит заявки только ради консолидации (приоритет 2), но
  не ради чистого сокращения пробега (приоритет 3) — это довольно редкий
  случай выигрыша и не стал приоритетом при ограниченном времени.
- **Длительность работы** не приходит в исходном CSV (только двухчасовое
  окно), поэтому при импорте проставляется дефолт по навыку
  (`config.DEFAULT_DURATION_MIN`: локальные — 60 мин, подключение/дозаказ —
  90 мин, аварийные — 45 мин). Оператор может поправить длительность у любой
  заявки в интерфейсе.
- **Навык и район заявки фиксируются при создании** и не редактируются
  дальше (как и договаривались про навык; район получил тот же статус, т.к.
  тоже участвует в жёстком отборе). Окно, срочность, длительность и
  требуемый транспорт — редактируемы.
- **Состояние только в памяти процесса** — перезапуск backend обнуляет всё
  (офисы, инженеров, заявки, план). Для хакатон-демо это осознанный выбор
  в пользу простоты.
- Frontend не был собран и запущен вживую в этой среде (нет сети для
  `npm install`) — код проверен статически (esbuild: синтаксис всех файлов +
  граф импортов между ними), и все имена пропсов/методов API сверены
  построчно с backend. Первый `npm install && npm run dev` может вскрыть
  мелкие шероховатости, обычные для непротестированного UI-кода.
- **`run.bat` не был протестирован на настоящей Windows** — в этой среде нет
  Windows вообще, поэтому проверить его можно было только вычиткой
  (синтаксис `.bat`, логика `for /f`-парсинга `.env`, кавычки в `start`).
  Логика в целом стандартная и хорошо известная, но если что-то пойдёт не
  так при первом запуске — самый надёжный fallback всегда доступен: ручные
  шаги из раздела «Вручную, шаг за шагом» выше. `run.sh` для macOS/Linux
  частично проверен прямо в этой песочнице (до шага, требующего сеть для
  `pip install`) — логика до этой точки отработала корректно.

## Последний патч: что изменилось

- **Очередь аукциона**: Срочно (ручной флаг) → Авария → Новое подключение →
  Ремонт → время окна (`planner.py::_priority_order`, `models.py::SKILL_QUEUE_RANK`).
- **Названия типов заявок** в интерфейсе: «Ремонт» / «Новое подключение» /
  «Авария» (внутренние значения `local` / `connect` / `emergency` те же).
- **Оборудование** снова жёсткий критерий: `Engineer.equipment`,
  `Request.required_equipment`, причина отказа `equipment`. У заявок —
  необязательная колонка CSV «Требуемые инструменты» (список через запятую).
- **Импорт бригад** файлом `Бригада;Компетенции;Оборудование;;Транспорт` (UTF-8, `;`):
  вкладка «Инженеры» → «Импорт бригад из файла». **Транспорт у каждой бригады и район
  (блок «Район» под таблицей: строка «Район», под ней название) берутся из файла
  автоматически** — вручную задаётся только смена (её в файле нет). Поле района на
  форме заполняется само и не редактируется. Район должен совпадать с районом
  уже импортированных заявок (из него определяется офис). Повторный импорт дубли
  не создаёт. Пример — `backend/sample_data/brigady.csv`.
- **Дополнительное оборудование FMC / FTTB**: у бригады — «Оборудование для FMC»,
  «Оборудование для FTTB» или «Без дополнительного оборудования» (нет ни того, ни
  другого); названия — как в `brigady.csv`. У заявки тип подключения берётся из
  колонки CSV «Подключение» (FMC / FTTB / пусто) и задаётся вручную в форме.
  Для FMC/FTTB жёстко требуется соответствующее оборудование у бригады
  (`Request.all_required_equipment`), «пусто» идёт без доп. оборудования.
- **Оформление v2** (`frontend/src/styles.css`): графитовая основа + янтарно-оранжевый
  акцент, светлая тема — кремово-песочная. Прежнее оформление сохранено в
  `frontend/design-archive/styles.v1-amber-graphite.css`.
- **Район из имени файла** обрезается по первому «_»: `Восток_Синтетические_данные_новые_инструменты.csv`
  → район «Восток» (иначе он не совпадал с районом из файла бригад, и импорт бригад падал с
  ошибкой «Нет офиса для района»). Сопоставление районов не зависит от регистра, а в тексте
  ошибки перечислены существующие районы. Импортируйте сначала файл заявок, потом бригад.
- **Тип заявок у бригады = оборудование**: в форме инженера поля «Типы заявок» больше нет; навык
  выводится из основного оборудования (для ремонта → Ремонт, для подключения → Новое
  подключение, для аварийных работ → Авария). В расписании плана колонки выровнены сеткой.
  Календарь (datetime-local) следует теме (`color-scheme`). Кнопка «Обновить» на «Плане» и
  атрибуция на карте убраны.
- **Адаптивный интерфейс**: сетки схлопываются в одну колонку, таблицы
  прокручиваются внутри карточки, боковая панель на узком экране становится
  верхней полосой навигации (≤860 px), страница не уезжает по горизонтали.
- **Индикатор загрузки**: фоновый опрос статуса больше не включает его, а сам
  индикатор появляется только при ожидании дольше 0,5 с — «прыгающее» окно убрано.
- Статусов по времени / симулированного времени / «Завершено» нет — заявка либо
  назначена, либо не назначена, либо отменена (как до предыдущего патча).
- Проверки патча: `python3 selfcheck_patch.py` (нужен установленный `fastapi`).

Полная и всегда актуальная схема — на `http://localhost:8000/docs`
(Swagger UI, генерируется FastAPI автоматически).

- Распределённая заявка проходит статусы: «Отправлено» → «В пути» (с момента выезда бригады) → «В работе» (бригада на месте, идёт работа) → «Завершено» (работа закончена). «Отменена» и «Не назначена» — как раньше.
